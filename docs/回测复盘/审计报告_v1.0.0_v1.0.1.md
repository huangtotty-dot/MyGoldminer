## 二、代码深度 Review：问题清单

### P0 级——导致系统性失效（必须最先修）

**P0-1 【v1.0.1】日内计数器永不复位 → 策略 3 天后永久瘫痪**
`main.py` 中 `context.daily_buy_count` / `daily_sell_count` 只有递增（L334/L358），**全文件无任何按日重置逻辑**。配合 `STOCK_PARAMS["000988"]` 的 `max_buy_times_per_stock=3`、`max_sell_times_per_stock=2`：04-28 买满 3 笔、05-21 卖满 2 笔后，所有后续买卖被 `bc >= max_buys` / `sc >= max_sells` 永久拦截。**这是 44 个交易日零交易的直接根因。**
建议检查点：`v1.0.1/main.py:144-145`（初始化）、`main.py:326,348`（拦截判断）。

**P0-2 【v1.0.1】引擎状态函数空实现 → 冷却/计数/闭环全部失效**
`signal/engine.py:527-531`：`record_signal()` 和 `record_trade_action()` 函数体是 `pass`。引擎内 `buy_cooldown`、`buy_count_per_stock`、`cycle_count`、`awaiting_buyback` 等 12 个状态字典在 `__init__` 声明后**从不更新**（`_check_date_reset` 每天都在清空一堆永远是空的字典）。后果：3 笔买单在 14:47/48/49 **三个连续分钟无冷却连发**；06_T V1.30 的轮次管理、高抛后低吸闭环、峰值跟踪全部不存在。
建议检查点：`v1.0.1/signal/engine.py:411-431, 527-531`。

**P0-3 【v1.0.0 & v1.0.1】底仓 5000 股超出购买力，首单即拒，且两版都用"幻象仓位"继续决策**
000988 股价 110~185 元，5000 股需 57~92 万，初始资金仅 20 万。两版首笔委托（5000 股市价买）均被拒（日志首条 WARN）。v1.0.0 的注释"华工科技约25-35元"是掘金浦发银行官方示例的残留。更严重的是：

### P1 级——保真性坍塌（融合版名不副实）

**P1-4 【v1.0.1】daily_ctx 全是硬编码桩 → 日线门控/多周期上下文整体失效**
`main.py:105-129` `_build_daily_ctx()` 返回固定值：`daily_ma5/10/20=0`、`daily_prev_close=0`、`daily_day_ret=0`、`daily_status="ok"`。持仓的 `pre_close` 被设为当前价（`main.py:283`）→ `today_ret`、`open_gap` 恒为 0 → 06_T 引擎中所有依赖日线位置/涨跌幅的因子（深亏监控、开盘急跌惩罚、大盘门控）在数学上全部失灵。

**P1-5 【v1.0.1】大盘态势三重退化**

- `_detect_inner()` 每次调用从 `prev_regime=RANGE, days_in_regime=0, s_prev=None` 重新起步（`index_regime.py:719-723`）→ 带滞回确认的状态机退化为单次分类；

**P1-6 【v1.0.1】疑似 VWAP 单位错误（需一行验证）**
`data/indicators.py:92`：`vwap = cumsum(amount) / (cumsum(volume) * 100.0)`。×100 是 06_T 腾讯数据源（volume 单位为**手**）的遗留；掘金 bar 的 volume 单位为**股**。若属实，VWAP 缩小 100 倍 → `score_vwap_buy` / `score_vwap_sell` 双因子退化恒满分（买卖各白送 20 分），整个评分体系失真。
验证方法（一行）：在 on_bar 打印 `amount/volume` 与 `close` 的比值，若 ≈100 则确认。

**P1-7 【v1.0.1】无止损/恐慌卖出通道 → 底仓穿越 -41% 暴跌**
简化引擎的卖出分只会在强势时产生（RSI 超买、VWAP 溢价、MACD 正区萎缩）；单边阴跌中 sell_score 恒低于阈值，且没有 06_T 的 PANIC_SELL / is_deep_loss 退出 / 指数熔断清仓 / 卖出地板保护。`RiskManager` 只有 6 条简单规则，`is_deep_loss` 特征算出来却从未被使用（`engine.py:344`）。06_T V1.30 的卖出端保护体系（底仓地板 50%、止损联动、熔断显性化）**完全未移植**。

## 三、改进计划

### 3.1 总体路线：绞杀者模式，三个迭代

不要试图一次性把 06_T V1.30（3000+ 行、20+ 场景因子）搬进掘金。按"先能跑对、再跑得像、再跑得好"分三步：

| 迭代 | 目标 | 验收门槛 |
|---|---|---|
| **v1.1.0 跑对** | 修掉 P0/P1 全部失效点：策略在整个回测期持续有交易、无幻象仓位、有止损、费用口径统一 | 三市况分段回测硬指标全过（见 3.3 T2） |
| **v1.2.0 跑得像** | 决策保真：同一交易日与 06_T 回放器（replay_day.py）的信号对照一致率 ≥ 70% | 信号对照报告（见 3.3 T3） |
| **v1.3.0 跑得好** | 参数寻优与样本外验证，接入 06_T 的 Optuna 体系 | 样本外不劣化（同 06_T Phase B3 口径） |

### 3.2 v1.1.0 设计优化方案（按优先级）

**D1. 状态层修复（对应 P0-1/P0-2）**
- 在 `on_bar` 入口检测日期变化：`if now.date() != context.cur_date:` → 重置 `daily_buy_count / daily_sell_count / daily_trade_price`，同时调用引擎的日期复位。
- 实装 `record_trade_action()`：写入冷却到期时间（`buy_cooldown[code] = now + cooldown_minutes`）、递增引擎计数、cycle 管理。编排层在**成交回调**（而非下单时）调用它。

**D2. 持仓与底仓真实化（对应 P0-3、P2-13）**
- 底仓数量按资金反推：`base_qty = floor(cash × base_position_pct / price / 100) × 100`（如 20 万 × 50% ÷ 115 ≈ 800 股），废弃写死的 5000。
- 底仓成交前 `_base_settled` 不得置位；在 `on_order_status(status==3)` 才入账，拒单（status 异常）计数并打印告警。
- `manual_position` 只作即时缓存，**每 30 分钟与 `context.account().positions()` 对账一次**，不一致以掘金侧为准并记录偏差事件。v1.0.0 文档中"SZSE get_position 不可靠"的假设需要重新验证（先在回测里打一行 positions 输出确认），不要作为设计前提。
- T+1：`available` 按"昨持仓"维护，当日买入只加 `qty` 不加 `available`，次日 09:31 结转。

**D3. daily_ctx 实装（对应 P1-4）**
- 每日首根 bar（或 09:25）用 `history_n(symbol, '1d', count=120, end_time=前一交易日)` 拉标的日线，计算 `daily_ma5/10/20`、`daily_prev_close`、`daily_day_ret`、`daily_breakdown_risk` / `daily_overheated`（规则可直接照搬 06_T 的 daily_ma 判定参数），注入 daily_ctx。
- 持仓 `pre_close` 用真实昨收，不要用成本价/当前价。
- 注意 GM 回测中 `history_n` 遵循回测时钟，无未来函数；但**必须显式传 end_time=昨日**，避免当日未收盘日线污染 open_gap 计算。

**D4. 大盘态势修复（对应 P1-5）**
- 每个交易日判定一次（09:31 首判即可），`as_of=当日`，日内缓存结果；删除"每分钟全量重算"。
- 在 on_bar 内按回测时钟重新 `history_n` 指数日线（而不是 init 一次性冻结）。
- env 数据源降级（qvix/广度/涨停池）要在每日日志中显性声明 `degraded=[...]`，不得静默。
- 异常必须打印，禁止 `except: pass`。

**D5. 止损与卖出保护通道（对应 P1-7）**
最小可用集（先移植这 4 条，再谈全量场景因子）：
1. 深度亏损退出：`profit_pct < -5×ATR` 且价格反弹无力 → PANIC_SELL；
2. 指数熔断：`index_regime=uni_down` 时禁止买入 + 卖出加分（参数表里 `index_clear_sell_boost` 等都在，接上线即可）；
3. 卖出地板：净持仓不得低于 base × 0.5（06_T 的 sell_floor_ratio）；
4. 尾盘规则：14:50 后未闭环的 T 仓强制归位（这才是"日内回转"的语义，v1.0.1 连尾盘回转都丢了）。

**D6. VWAP 单位验证（对应 P1-6）**
- 一行验证：`print(amount/volume, close)`，比值 ≈100 → 删除 `*100.0`；≈1 → 保留并注释数据源差异。
- 验证后把该用例固化进单元测试（见 T1-3）。

**D7. 评分与参数保真声明（对应 P2-9/P2-11）**
- 二选一：要么完整移植 06_T 场景因子（v1.2.0 的事），要么把 `params.py` 砍到只保留实际生效的 ~20 个参数，并在文件头声明"GM 版为简化评分引擎"。消除保真度假象。
- 阈值判定收拢到引擎一层，编排层不再二次拦截；`notify_sell_early_threshold` 的时段逻辑下沉进引擎。

**D8. 审计链路（对应 P2-12）**
- 每 bar 落一行 decision JSONL（时间/scores/blocks/reason/持仓），成交落虚拟账，日终写 summary。这是后续所有复盘与 K3 式审计的基础设施，**优先级应高于任何因子移植**。
- 回测结束 `on_backtest_finished` 输出：成交笔数、拒单笔数、闭环数、FIFO 盈亏、费用占比——与掘金指标互相印证。

**D9. 回测口径统一（对应 1.3、P2-14）**
- `run()` 显式写死：`commission_ratio=0.00015`（与 06_T PARAMS 一致）、`slippage_ratio=0.0001`、`adjust=ADJUST_PREV`；分红处理口径写进 README。
- 主报告用 `match_mode=1`，附 `match_mode=0`（下一 bar 开盘）敏感性对照，两者差异 >20% 时以保守口径为准。

| T3-2 | v1.1.0 vs 06_T 回放器同日信号 | 同向信号一致率 ≥ 70%，不一致条数逐条可解释 |
| T3-3 | 费用敏感性（0 / 1bp / 3bp 佣金三档） | 3bp 下收益仍为正，否则策略对费用过敏、不具备实盘性 |
| T3-4 | 样本外（2025-09 ~ 11，同 06_T Phase B3 窗口） | composite 不劣化于默认参数 × 100%，闭环数 ≥ 90% |

**T4 准实盘（仿真 5 个交易日）**
- 掘金仿真模式与 06_T t_trader 实盘并行跑 5 天，每日收盘对照信号清单（时间/方向/价格带），输出一致性日报；拒单 = 0、异常栈 = 0 方可谈实盘切换。

### 3.4 明确不做的事

- 不在 v1.1.0 阶段移植全部场景因子（先保证框架正确，因子是 v1.2.0 的事）；
- 不在计数器/持仓修复前做任何参数调优——**在瘫痪的策略上调参等于掷骰子**；
- 不删除 06_T 回放体系——掘金版必须与 replay_day.py 长期共存互验，两套独立实现互为审计；
- v1.0.0 的 MACD 策略不抢救、不调参，直接归档为管线验证脚手架。

## 四、审计结论

1. **v1.0.0**：管线验证成功（订阅/下单/撮合/指标计算全链路可用），策略本身负期望，归档。
2. **v1.0.1**：融合在架构方向上正确（模块化拆分、移除 akshare、数据注入大盘态势），但**状态层三个 P0 缺陷使策略在 97% 的时间里处于瘫痪/幻象仓位状态**，+8.43% 的 KPI 是 5 笔交易的幸存者偏差，不能作为融合成功的证据。
3. **优先序**：先修 D1/D2（状态与持仓）→ D8（审计链路）→ D3/D4/D5（上下文与止损）→ 重跑三市况 → 再谈保真与寻优。
4. 修复工作量评估：D1+D2+D6+D8 约 1 天；D3+D4+D5 约 1 天；T2 三市况验证半天。**预计 2.5 天可交付 v1.1.0 并完成第一轮硬指标验收。**
