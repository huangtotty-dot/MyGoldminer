### N8 假现金 → ✅ 修复到位

- **代码**（main.py:606-624）：`getattr(_acct,'cash')` → `callable` 判断 → dict 多键名兼容（available/available_cash/cash/total），与审核建议的修法一致；新增 `_cash_warned` 一次性 WARN，静默 except 已去静默化。

### N9 PANIC 止损自解除 → ✅ 修复到位（行为级验证），附两个设计注记

- **代码**（engine.py:349-355）：`_panic_trigger = max(-5×daily_atr, -12% 固定下限)`，并新增 `panic_trigger`/`panic_atr_line` 观测字段（正是审核建议的审计字段）。
- **行为证据（关键）**：fix3 持仓成本 166.95，-12% 触发线对应价格 ≤146.9。7 月 6 笔卖出全部贴合触发线（143.58 / 146.66 / 146.90 / 146.91），07-08 起逐笔减仓，**07-15 14:33 清仓至 0 股**，随后 07-16 收 130.69、07-20 收 105.86——止损机制第一次真实救了账户。MDD -8.65% vs fix2 -21.2%。
- **设计注记 1（⚠️ 知晓即可）**：`max(-5×ATR, -12%)` 的数学效果是——只要日 ATR > 2.4%（000988 几乎永远成立），ATR 项即被 -12% 下限覆盖，**实际等价于固定 -12% 止损**。这符合"触发线始终可达"的修复意图，但意味着 -5×ATR 项实质成为死代码，建议择期简化或注释说明。
- **设计注记 2（⚠️ 鞭打风险）**：07-14 09:41 PANIC 卖在 143.58（当日最低 142.71 附近），当日却 V 形反转收 159.84——本窗口因暴跌延续而净受益，但固定 -12% 止损在深 V 日会卖在坑底。这不构成否决项，建议纳入周度复盘的"PANIC 鞭打率"观测指标。

### N10 sizer 死亡 → ✅ 修复到位

- **代码**（main.py:626-636 + position_sizer.py:70-82）：main 侧用真实现金算出仓位上限约束下的 `target_t` 传入 sizer；sizer 新增 target_t 语义与 `hold_qty×1.5` 的合理兜底。
- **行为证据**：fix3 买入股数 100/200/300 按信号强度分级变化（fix2 全部恒 300），同日多笔买入量随仓位水位递减（如 06-29 的 100→200、06-17 的 200→100），sizer 真实参与决策。

### N11 费用口径 → ❌ 未闭环（代码对、结果错）

- **代码层 ✅**：params.py:21 `commission_rate=0.00015`（与 fix1 一致），main.py:829-832 设置了 ADJUST_PREV + commission + slippage 0.0001。
- **结果层 ❌**：v1.0.1_fix3 回测 64 条资金记录 **fee 全为 0.0**，与 fix2 同为零费用口径。fix3 的 +16.34% 与 fix1（含费）仍不可直接比较。
- **根因方向**：见 N13——main.py 的 mode 配置互换导致 `backtest_commission_ratio` 在 MODE_LIVE 下被忽略；或该报告由掘金终端 UI 默认参数生成（UI 默认佣金为 0）。**建议 Pro 检查**：确认该报告的实际生成路径（终端回测对话框 or `__main__` 块），修正 N13 后用显式 `mode=MODE_BACKTEST + commission` 重跑同窗口。

### N12 run_id 全空 → ✅ 代码修复 / ⚠️ 结果不可验证

- **代码层 ✅**：main.py:818 `_AUDIT_RUN_ID` 在模块级赋值（`if __name__` 块内即模块作用域），global 缺失问题解决。
- **结果层 ⚠️**：fix3 回测**未在项目目录留下 gmcache/backtrace.jsonl**（目录不存在），无法从产物验证 run_id 实际写入，也无法核对拒单计数。**这同时是一个验收证据缺口**：本轮回测疑似由掘金终端/云端环境执行，审计文件未落本地。周一模拟盘上线前必须确认终端运行时 gmcache/backtrace.jsonl 会真实生成（操作手册 4.2 节已依赖该文件）。
