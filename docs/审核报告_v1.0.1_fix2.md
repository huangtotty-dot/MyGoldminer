## 一、结论速览

**⚠️ 重大进步，但 T2 八项门槛仅过 4 项 —— 判定：不可进入 Optuna 参数寻优，需 fix3。**

fix2 做对了最重要的一件事：**卖强通道彻底打通**。strong_uptrend 禁卖移除后，5-6 月 17 笔卖出全部成交在 132→184 的递增价位上，100% 胜率（17/17），把 fix1 的"满仓死扛 -6.05%"扭转为 **+18.29%、夏普 1.18、回撤 21.2%**，大幅跑赢同期买入持有（≈ -5.5%）。这证明信号引擎的卖出侧是真实有效的，N1 修复方向正确。

1. **现金/仓位双保险形同虚设（N8）**：`account().cash` 属性被当方法调用，异常被静默吞掉，永远用假现金 100,000 计算 —— 导致 6 条柜台拒单、仓位一度冲到 1,700 股（≈99.5% 满仓），N2/N3 两项修复全部落空。

3. **仓位计算器实际死亡（N10）**：t_qty≡qty 导致 max_buyable 恒为 0，sizer 恒返回 0，全部买入走 fallback 固定 300 股 —— 仓位管理名存实亡。

另有费用口径回退（N11，fix2 未设佣金/滑点，与 fix1 不可直接比较）和审计 run_id 未生效（N12）两处工程瑕疵。

## 四、新发现问题（N8 ~ N12）

### N8 ❌【P0】`account().cash` 属性当方法调用 → 现金预检与仓位上限双双失效

- **预期**：读取账户真实可用现金，超上限/现金不足时拦截买入。
- **实际**：main.py:526 `available_cash = float(_acct.cash())` —— gm3 的 `account().cash` 是**属性（dict）而非方法**，调用即抛 TypeError，被 527-528 行 `except Exception: pass` 静默吞掉，`available_cash` 永远保持默认值 100,000。
- **行为证据链**：
  1. 假现金 100,000 使 N3 预检分母失真 → 04-30~05-07 六条柜台拒单"资金不足 可用=900.999"（预检放行、柜台拒绝）；
  2. N2 仓位上限用 `available_cash + current_pos_value` 做总权益分母（main.py:539）→ 04-29 10:36 真实仓位 82% 仍成交，04-30 达 1,700 股 ≈99.5% 满仓。
- **根因方向**：API 形态误判 + 静默 except 掩盖故障。静默 except 是二次伤害——若吞错时打印一次告警，此 bug 在首次回测就会暴露。
- **建议 Pro 检查**：`main.py:522-542`。修法参考（不改任何阈值）：
  ```python
  c = getattr(_acct, 'cash', None)
  c = c() if callable(c) else c
  available_cash = float(c.get('available', 0) if isinstance(c, dict) else c)
  ```
  并把 `except Exception: pass` 改为至少一次性 WARN 输出。

### N9 ❌【P0】PANIC 止损"自解除"：-5×日ATR 触发线随暴跌放宽，全程不可达

- **预期**：深度浮亏时 PANIC 强平，185→108 主跌段至少触发 1 次。
- **实际**：7 月 18 个交易日 0 笔交易；backtrace.jsonl 显示每日 sell_blocks 全空、reason 全"无信号"。
- **数据验证**（审计员用独立日线数据复算：archive 日线 CSV 至 07-06 + 分钟快照重建 07-07 起，TR14/close）：

  | 日期 | 收盘 | 日ATR% | 触发线(-5×ATR) | 相对成本162.14浮亏 | 应触发? |
  |---|---|---|---|---|---|
  | 06-24 | 167.89 | 5.7% | **-28.7%** | +3.5% | 否 |
  | 07-06 | 149.70 | 8.1% | **-40.3%** | -7.7% | 否 |
  | 07-16 | 130.69 | 9.8% | **-49.0%** | -19.4% | 否 |
  | 07-20 | 105.86 | 11.7% | **-58.7%** | -34.7% | 否 |
  | 07-24 | 108.19 | 10.3% | **-51.6%** | -33.3% | 否 |

  23 天逐日对照：**hit 天数 = 0**（按收盘与按盘中最低价均为 0）。ATR 从 5.7% 爆炸到 11.7%，触发线同步放宽，浮亏永远追不上触发线——**越暴跌越不止损**。
- **根因方向**：engine.py:349 `is_deep_loss = profit_pct < -5 * daily_atr`，ATR 系数无上限。波动率自适应止损在单边暴跌中必然自解除，这是设计缺陷而非参数问题。
- **建议 Pro 检查**：`signal/engine.py:345-349`、`main.py` daily_atr 计算段。修复方向（属设计修正，不涉及买卖阈值数值调优）：触发线改为 `max(固定下限如 -12%, -5×ATR)`，或对 ATR 封顶（如 `min(daily_atr, 0.03)`），保证止损线始终可达。
- **诚实标注**：复算基于 tushare 日线+分钟快照重建，与 gm3 回测内部 daily history 可能有微小差异，但 ATR 量级（5.7%→11.7%）与结论稳健；即使成本口径不同，-40%~-59% 的触发线在实践中也不可达。

### N10 ❌【P1】position_sizer 实际死亡：t_qty≡qty → max_buyable 恒 0 → 全部买入走 fallback 300 股

- **预期**：sizer 按信号强度与仓位结构计算加仓位。
- **实际**：position_sizer.py:56 `total_t = t_qty or qty`，:70-71 `hold_qty = qty; max_buyable = total_t - hold_qty` —— 融合版持仓模型中 t_qty 与 qty 始终同步相等，max_buyable 恒为 0，:73 恒返回 0。main.py:519-520 兜底 `qty = 300`。
- **行为证据**：成交 CSV 全部买入均为 300 股整（04-29、04-30、05-18、06-01…06-25），无一笔由 sizer 算出。
- **根因方向**：T 仓语义未在持仓模型中区分——t_qty（目标 T 仓）与 qty（当前持仓）在融合层被同步更新，sizer 的"剩余可买额度"概念落空。
- **建议 Pro 检查**：`signal/position_sizer.py:55-77` 与 main.py 持仓同步段。需要在持仓模型里真正区分 base/t_qty/qty 三层语义，或在融合层为 sizer 提供独立的"目标仓位"输入。

### N11 ❌【P1】D9 费用口径回退：fix2 回测未设佣金/滑点/复权

- **预期**：延续 fix1 口径（commission=0.00015 等），保证版本间可比。
- **实际**：fix2 回测请求缺 commission/slippage/adjust 参数，成交 CSV fee 全 0.0。fix2 +18.29% 为零费用口径，约高估 0.5~1 个百分点；与 fix1（-6.05%，含费）不可直接对比。
- **建议 Pro 检查**：回测发起脚本/参数。fix3 重跑时必须固定统一口径，并在报告头部声明。

### N12 ⚠️【P2】审计 run_id 未生效

- **实际**：`_AUDIT_RUN_ID` 在函数内赋值未声明 `global`，backtrace.jsonl 14,160 行 `_run_id` 全为空串。多 run 混排时无法区分来源（本次为单 run，暂未造成混淆）。
- **建议 Pro 检查**：main.py 中 `_AUDIT_RUN_ID` 赋值处，补 `global _AUDIT_RUN_ID`。

## 六、总体结论与 fix3 优先序

### 结论

**不可进入 Optuna 参数寻优。** fix2 证明了信号引擎卖出侧的真实有效性（这是本轮最重要的正面结论），但 N8/N9/N10 三个实现级缺陷分别架空了现金风控、止损与仓位管理三大安全网。在假现金、无止损、死 sizer 的系统上做参数寻优，只会把 bug 当成 alpha 拟合进去。

### fix3 优先序（均为一行级~小范围修复，不涉及买卖阈值数值调整）

1. **N8（P0）**：main.py:522-542 修正 cash 属性读取 + except 去静默化。预期效果：拒单归零、仓位上限真实生效（fix2 的 1,700 股超仓将不再出现，KPI 会因此变化，属正常）。
2. **N9（P0）**：engine.py:349 止损触发线加下限/ATR 封顶（设计修正）。预期效果：07-16 前后（浮亏 -19.4%、触发线若有 -12% 下限）应出现 PANIC 卖出，fpnl -43,163 的底仓深套可截断约一半。
3. **N10（P1）**：理清 t_qty/qty 语义，让 sizer 复活或显式声明"固定 300 股"为当前设计。二选一，不要继续让死代码伪装成活风控。
4. **N11（P1）**：fix3 回测统一费用口径（沿用 fix1 的 commission/slippage/adjust），报告头部声明口径。
5. **N12（P2）**：补 global 声明，顺手在 no_signal 记录里加上 profit_pct / daily_atr / is_deep_loss 三个字段——本次 N9 的复算验证本可由审计记录直接给出，不必外部重建日线。

### fix3 验收标准（预告）

- T2 八项全绿（重点看 #1 拒单=0、#5 主跌段止损≥1 次、#7 口径一致）；
- 接受 KPI 回撤：修复 N8/N9 后收益大概率低于 +18.29% 的虚高值，**这是健康的方向，不是退步**——fix1→fix2 教会我们"能赚",fix3 要证明"亏不了大的"。
