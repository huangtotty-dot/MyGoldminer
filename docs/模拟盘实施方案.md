## 第一部分：对三个设想的专家评估

### 设想 1：模拟盘镜像被套持仓，辅助实盘回本 —— ⚠️ 方向靠谱，但定位必须修正

**一个根本性逻辑问题必须先说清楚：模拟盘的做 T 盈利不会进入你的实盘账户。** 模拟账户 +18%，实盘的套牢成本一分钱都不会降。回本这件事，只有真实账户里的 T 差价能做得到。

所以这个设想的正确定位不是"用模拟盘回本"，而是：

> **模拟盘 = 信号源 + 验证场。模拟盘跑出买卖信号 → 你在实盘跟随执行 → T 的差价真正发生在实盘，成本才真的下降。**

在这个修正后的定位下，设想完全成立，且有三个额外好处：

1. **零风险验证个股适应性**：当前策略只在 000988 单票上验证过。你被套的其他股票波动结构、流动性、股性都不同，直接在实盘跑等于拿真钱做 A/B 测试；模拟盘先把"这套信号在这只票上灵不灵"测出来。
2. **信号可信度有参照系**：模拟盘信号与你的实盘持仓完全同构（同票同股数），信号的出现时点、价位、仓位变化可以直接对照实盘决策，不存在"回测很美但跟实盘对不上"的断层。
3. **心理缓冲**：有模拟盘先跑一遍，实盘跟随时是"第二次看到这只票的这个信号"，决策质量会高得多。

**三个必须面对的风险（都有审计依据）：**

| 风险 | 依据 | 对策（详见 Phase 0） |
|---|---|---|
| N9 止损自解除未修复：暴跌时 PANIC 不可达，模拟盘和跟随的实盘都会深套 | fix2 审核：-5×日ATR 触发线暴跌期放宽至 -58.7%，23 天 0 触发 | 人工止损纪律 + 监听层旁路告警，实盘跟随单必须自带止损价 |
| 个股适应性未验证：000988 的阈值参数直接套到别的票上，可能完全失效 | 全部回测/审计仅覆盖 000988 | 逐票评估做 T 门槛，新票先观察 3~5 天再允许跟随 |
| 模拟撮合偏乐观：无真实排队、冲击成本，成交价比实盘好 | 模拟盘固有属性 | 所有 KPI 标注"模拟口径"，滑点分析纳入日复盘 |

### 设想 2：自动交易 + 飞书通知 —— ✅ 完全靠谱，资产现成

E:\06_T 已有成熟的飞书推送基建（`config.py:103 send_feishu_payload`、webhook 解析、启动自检、加急告警机制），t_trader 的告警体系久经实盘考验。唯一需要工程决策的是：**通知逻辑不要写进 gm3 策略进程内**，理由：

1. gm3 沙箱的网络权限不确定，策略内 `requests.post` 可能直接被拦；
2. 策略进程崩溃 = 通知能力同时丢失，恰恰是出事时你最需要通知；
3. 通知代码污染交易策略，违背模块化重构的成果。

**推荐文件桥架构**（详见第二部分）：策略只往本地写事件文件，独立监听进程读文件推飞书。单向、可重放、可审计。

### 设想 3：每日模拟盘质量复盘 —— ✅ 完全靠谱，基建大部分现成

引擎本来就写 backtrace.jsonl（每笔决策可追溯），`t_trader-daily-feedback-loop` 复盘流程、`t_io/reviews/` 目录体系、分钟快照机制都在。缺的是三块：gm3 模拟盘数据采集器、模拟盘专属质量 KPI 层、以及"模拟 vs 回测"一致性对比。第四部分给出完整设计。

### 总评

**三个设想组成闭环：模拟盘验证（设想1）→ 信号送达（设想2）→ 质量复盘反哺优化（设想3）。方向正确，值得做；前提是接受"模拟盘是信号源而非回本工具"的定位修正，并把 N9 未修的风险用人工护栏兜住。**

## 第二部分：总体架构（三层解耦）

```
┌─────────────────────────────────────────────────────────────┐
│ L1 执行层：gm3 模拟盘（融合版策略）                            │
│   职责：跑信号 → 下单 → 把事件写入文件桥                       │
│   唯一新增职责：on_signal/on_order_status/on_execution_report │
│   里追加写 E:\06_T\t_io\gm_bridge\events_YYYYMMDD.jsonl      │
│   （只写文件，不碰网络，不碰飞书）                             │
└──────────────────────┬──────────────────────────────────────┘
                       │ 文件桥（单向、可重放、可审计）
                       ▼
┌─────────────────────────────────────────────────────────────┐
│ L2 桥接层：E:\06_T\t_io\gm_bridge\                           │
│   events_YYYYMMDD.jsonl   当日事件流（schema 见附录 A）        │
│   heartbeat.json          心跳（策略每分钟刷新时间戳）          │
│   KILL_SWITCH             急停文件（存在即禁止新开仓）          │
│   follow_log.jsonl        实盘跟随记录（人工登记）              │
└──────────────────────┬──────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────┐
│ L3 通知与复盘层（E:\06_T 进程，复用现有基建）                  │
│   gm_watcher.py   监听事件桥 → config.send_feishu_payload    │
│                   去重/限流/聚合/心跳监控/旁路风控告警          │
│   每日复盘任务    15:30 收盘后采集+分析+飞书简报+本地存档       │
│   周度深度审计    每周六，K3（审计员）主持                     │
└─────────────────────────────────────────────────────────────┘
```

**设计原则**：策略进程只增加"写文件"这一个无副作用动作；通知、复盘、风控旁路全部在外部进程，任何一环挂掉不影响交易主链路，且事件文件可重放补推。

## 第三部分：实施计划（按时间线）

### Phase 0：周末准备（7/25 周六 ~ 7/26 周日）

#### 0.1 版本确认与风险定级【最先做，决定后续所有事】

- 确认周一上线的 commit。若 fix3（修 N8 假现金 / N9 止损自解除 / N10 sizer）**尚未完成并通过验收**，则上线版本为带已知缺陷的 fix2，必须执行以下强制护栏：
  - 人工止损纪律写进每日操作清单（弥补 N9）：任何镜像持仓浮亏超过 -12% 即触发人工评估，不依赖策略 PANIC；
  - 监听层旁路监控仓位与现金（弥补 N8）：watcher 独立跟踪仓位市值占比，超 80% 即飞书加急告警；
  - 单票买入固定 300 股视为当前既定行为（接受 N10 现状），仓位预期管理按此做。
- 明确铁律延伸：**模拟盘测试期间不改买卖阈值**；所有参数变更走"提出→审计→commit→重跑"流程。

#### 0.2 标的与参数清单

建立《模拟盘标的清单表》，逐票填写：

| 字段 | 说明 |
|---|---|
| 代码/名称 | 被套个股 |
| 实盘成本/股数 | 仅作参照，不进模拟盘逻辑 |
| 模拟镜像股数 | 建议与实盘一致（保持信号同构）；底仓 base_ref 按此设定 |
| 做 T 门槛评估 | 日均振幅 >3%、日成交额 >2 亿，二者不满足的票标记"仅观察不跟随" |
| 参数来源 | 000988 直接继承现有参数；新票第一版沿用同套参数，标注"未适配" |
| 上线批次 | 周一仅 1 只（建议 000988 或套得最深且满足门槛者），周二起每 1~2 天加一只 |

#### 0.3 模拟账户设置

- 资金规模：按镜像持仓总市值 ×1.3 配置（留足做 T 现金水位）；
- **佣金/滑点口径必须与回测统一**（沿用 fix1 的 0.00015 口径，不要重蹈 N11 费用口径回退的覆辙），并在账户设置截图存档；
- 建仓方案与 T+1 约束（**关键认知**）：周一买入的底仓当天不可卖，**周一实际只能"建仓 + 观察信号"，真正的做 T 从周二开始**。周一的成功定义见 Phase 1，不要因为周一没有 T 交易而误判系统故障；
- 底仓建仓方式：开盘后按 base_order 逻辑一次性买入镜像股数，价格以实盘成交价为准记录偏差。

#### 0.4 文件桥 + 飞书联通测试

- 定义事件 schema（附录 A），策略侧在 4 个回调点追加写文件（信号、委托、成交、拒单）+ 每分钟心跳；
- 编写 `gm_watcher.py` 监听进程：tail 事件文件 → 复用 `config.py:103 send_feishu_payload` 推送，带三个机制：
  - **去重限流**：同一事件 ID 不重复推；盘中信号类通知按票聚合，避免刷屏；
  - **心跳监控**：10:00 前未收到任何心跳/事件 → 推"策略可能未启动"加急告警；盘中心跳中断超 10 分钟 → 加急告警；
  - **旁路风控**：独立累计仓位与现金，超上限即告警（不依赖策略自身的 N8 逻辑）；
- 联通测试 checklist：周日用回放事件文件的方式测试 watcher（构造假事件 → 验证飞书收到 → 验证去重 → 验证告警格式），不动策略本身。

#### 0.5 风控护栏与应急方案

- `KILL_SWITCH` 文件机制：在桥目录放置该文件，策略每分钟检查，存在即停止新开仓（平仓不禁）。用途：发现异常时无需登录 gm3 即可急停；
- 单日最大亏损线：账户日内浮亏超 3% → watcher 加急告警；超 5% → 建议人工放置 KILL_SWITCH；
- 终端/进程崩溃预案：gm3 终端崩溃后策略状态丢失，重启策略后底仓计数器如何恢复——**这是 fix2 审计中 P0-1 类问题的高发区，周一前必须人工演练一遍"崩溃→重启→核对仓位"流程**。

### Phase 1：周一（7/27）上线日 —— 定义"最小成功"

**周一的目标不是赚钱，是验证链路。** 成功标准（checklist）：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 策略启动 | 09:25 前策略运行，飞书收到启动自检 |
| 2 | 底仓建仓 | 镜像股数买入成交，飞书收到成交通知，价格偏差记录 |
| 3 | 事件桥 | events jsonl 全天持续写入，字段完整 |
| 4 | 心跳 | 全天无"心跳中断"告警（或告警后能定位原因） |
| 5 | 信号观察 | 即使不交易，no_signal/信号记录完整，收盘能回答"今天为什么没动作" |

### Phase 2：周二 ~ 周五（7/28 ~ 7/31）稳态运行

**每日节奏表：**

| 时间 | 事项 |
|---|---|

| 09:15 | watcher 自检 + 策略心跳确认 |

| 15:30 | 每日复盘任务：采集 → 分析 → 飞书简报 + 本地完整报告存档 |
| 收盘后 | （可选）对照 t_trader 当日实盘信号，做双系统交叉验证 |

**实盘跟随规则（前两周 100% 人工确认，这是红线）：**

1. 只跟随"仅观察"标记以外的票；
2. 跟随前过 checklist：信号分数、当前仓位、现金、止损价（人工设定，弥补 N9）、跟随量（建议为模拟信号量的 50%~100%）；
3. 跟随价格与模拟成交价的偏差记入 follow_log，作为滑点分析素材；
4. 模拟盘发出卖出信号而你实盘不想卖（或反之）→ 同样登记，标注原因——**分歧记录比一致记录更有复盘价值**；
5. 任何情况下模拟盘信号不得自动直连实盘下单。

**加票节奏**：周二加第 2 只，周四加第 3 只，每只新票前 3 天标记"仅观察"。

### Phase 3：周度深度分析（每周六，首次 8/1）

- **模拟 vs 回测一致性**：同标的同窗口，信号时点/价位/仓位轨迹对比，量化"行为漂移"；
- **滑点与撮合偏差**：模拟成交价 vs 信号发生时价 vs 实盘跟随成交价，三方对比；
- **信号质量分层**：按信号类型（SELL_HIGH / 低吸 / PANIC）统计胜率、平均差价、持有期；
- **优化候选清单**：只列"值得改什么"，全部走审计流程，不直接动阈值；
- **K3 周度审计**：按既有审计员规则出周度报告，判定"是否允许扩大跟随规模/放宽人工确认"。

## 第四部分：每日复盘报告设计（质量 KPI 体系）

**数据采集三源合并**：gm3 模拟盘成交/委托导出 + 事件桥 jsonl + backtrace.jsonl + 分钟快照。

**五类 18 项质量 KPI：**

| 类别 | KPI | 健康线 |
|---|---|---|
| A 执行质量 | A1 柜台拒单数 | =0（N8 修复前允许>0，但每条必须归因） |
| | A2 信号→委托延迟 | <2 个 bar |
| | A3 委托→成交滑点 | 统计分布，关注系统性偏移 |
| | A4 尾盘归位执行率 | 100% |
| B 信号质量 | B1 买/卖分数分布 | 与回测分布对比，漂移>20% 标记 |
| | B2 no_signal 占比及原因分类 | 长期 >90% 需检查是否瘫痪（v1.0.1 教训） |
| | B3 信号→成交转化率 | 突降即查拒单/冷却 |
| | B4 卖强价位递增性 | 上升趋势中卖出价应递增（fix2 的正面特征） |
| C 风控有效性 | C1 仓位峰值/曲线 | 峰值 ≤80%（N8 修复前由旁路监控兜底） |
| | C2 现金水位 | 不做满仓 |
| | C3 止损/PANIC 触发记录 | 大跌日**应触发而未触发 = 红色警报**（N9 直接观测点） |
| | C4 uni_down 熔断命中 | 熔断日 0 买入 |
| D 盈亏归因 | D1 已实现 vs 浮动 | 拆分"卖强赚的钱"与"底仓套的亏"（fix2 的核心矛盾） |
| | D2 按票归因 | 哪只票的信号在赚钱 |
| | D3 按信号类型归因 | 哪类信号在赚钱 |
| | D4 做T差价 vs 底仓波动贡献 | 做T是否真在降低成本 |
| E 一致性 | E1 模拟 vs 回测同日信号重合度 | 趋势性下降即查数据/环境漂移 |
| | E2 模拟 vs 实盘跟随偏差 | 仅在有跟随时计算 |

**产出三件套**：

1. **飞书简报**（一屏）：当日成交、盈亏、风控状态、1~3 条最值得注意的异常；
2. **本地完整报告**：`E:\06_T\t_io\reviews\gm_sim\YYYYMMDD\`（KPI 明细 + 原始数据 + 异常证据）；
3. **周度汇总**：趋势图 + 优化候选清单。
